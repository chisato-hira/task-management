## 品質チェックの進め方

このスキルは、実装が完了したコードベース全体（または対象範囲）に対して、以下の4つの観点で総点検を行うためのもの。
すべての項目を確認し、見つかった問題は **同じブランチ・同じPRで一括対応する**（軽微な指摘も先送りにしない）。

ユーザーから対象範囲（特定機能・特定ファイルのみ等）の指定がない場合は、リポジトリ全体を対象とする。

---

## ステップ1：静的解析・ビルドチェック

### フロントエンド

```bash
cd frontend
npm run lint
npx tsc -b --noEmit
```

- ESLint・TypeScript ともにエラー0件であること
- warning が出ている場合も内容を確認し、無視してよいものか判断する

### バックエンド

```bash
cd backend
./gradlew build
```

- `BUILD SUCCESSFUL` であること（テスト含む）
- コンパイル警告（特に非推奨API・unchecked警告）が出ていないか確認する
- `./gradlew build` には Checkstyle チェック（`config/checkstyle/checkstyle.xml`、`maxWarnings = 0`）が含まれる。違反があれば `backend/build/reports/checkstyle/main.html` を確認し、内容を個別に判断する

### Terraform

```bash
cd terraform
terraform fmt -check -diff
terraform validate
```

- `terraform fmt -check` が差分なしであること（フォーマット崩れがないか）
- `terraform validate` がエラーなしであること（構文・参照エラーがないか）
- セキュリティグループで `0.0.0.0/0` を許可しているポートがないか確認する（自分のIP等、必要最小限の範囲に絞られているか）
- 変数定義（`variables.tf`）で、パスワード等の機密情報を扱う変数に `sensitive = true` が付与されているか
- `.tfvars`・`.tfstate`・SSH秘密鍵などが `.gitignore` で除外されているか（`git status` で追跡対象に入っていないか確認）

## ステップ2：デファクトスタンダードからの逸脱チェック

### バックエンド（Spring Boot）

- [ ] controller が JPA エンティティを直接 `@RequestBody` で受け取っていないか（mass assignment 対策として、作成・更新には専用 DTO を使う）
- [ ] `@Valid` + Bean Validation アノテーション（`@NotBlank` / `@Size` / `@NotNull` 等）が必須項目に付与されているか
- [ ] バリデーションエラーが日本語の分かりやすいメッセージとしてレスポンスに返るか（`spring.mvc.problemdetails.enabled=true` だけでは `detail` が `"Invalid request content."` という汎用メッセージになるため、`@RestControllerAdvice` でフィールドエラーを `detail` に詰め直す実装が必要）
- [ ] service 層に不要な null ガードや、リクエスト値を無視してしまう分岐がないか（例：description を空にして送っても更新されない、など）
- [ ] 自動採番・並び順などのロジックが、既存データの最大値を見て計算されているか（固定値 `0` 決め打ちなどになっていないか）

### フロントエンド（React / TypeScript）

- [ ] `useEffect` 内で同期的に `setState` を呼んでいないか（`react-hooks/set-state-in-effect` 違反）
- [ ] 全角スペースなど不可視文字が JSX 内に紛れていないか（`no-irregular-whitespace`）
- [ ] フォームの入力上限（`maxLength` 等）がバックエンドのバリデーションと一致しているか

## ステップ3：ドキュメントとの整合性チェック

`docs/` 配下および以下のドキュメントと実装を突き合わせる：

- `README.md`（プロジェクト概要・機能一覧・APIエンドポイント一覧）
- `docs/requirements.md`（要件定義書）
- `docs/functional-requirements.md`（機能仕様書）
- `docs/screen-design.md`（画面設計書）
- `docs/tech-stack.md`（技術スタック・APIエンドポイント一覧）
- `docs/database-design.md`（DB設計書）
- `docs/aws-infrastructure.md`（AWSインフラ構成）

確認項目：

- [ ] 実装済みの API エンドポイント・リクエスト/レスポンス形式が `tech-stack.md` の記載と一致しているか
- [ ] README.md の機能一覧・APIエンドポイント表が実装、および `tech-stack.md` の記載と一致しているか（表記揺れも含む）
- [ ] 画面のワイヤーフレーム・入力項目（UIコンポーネントの種類含む）が `screen-design.md` と一致しているか
- [ ] 機能要件（`functional-requirements.md`）を満たす実装になっているか
- [ ] `database-design.md` のテーブル定義が、実際のEntity（`@Entity`クラスのフィールド・型・制約）と一致しているか
- [ ] `tech-stack.md` に記載のバージョンが、実際の依存関係（`build.gradle.kts`・`package.json`）と一致しているか
- [ ] `aws-infrastructure.md` の構成説明が、`terraform/`配下のコードおよび実際にデプロイされている構成と一致しているか

**差異が見つかった場合の対応方針：**

- 実装側にバグ・要件漏れがある → 実装を修正する
- 実装は正しいがドキュメントが古い・実装後の変更が反映されていない → ドキュメントを実装に合わせて更新する
- どちらが正か判断がつかない場合 → ユーザーに確認してから対応する（一度に1つずつ質問する）

## ステップ4：エラー隠蔽チェック（必須）

問題を「動いているように見せかけて」隠していないかを必ず確認する。

エラー処理は個々の箇所だけでなく、発生源（例外スロー箇所）→ 通信層（レスポンス/エラーハンドリング）→ 画面表示まで1本の線として実装を追い、途中で情報が欠落・上書き・無視されていないかを確認する。

- [ ] `catch` ブロックで例外を握りつぶし、何もログ・表示をしていない箇所がないか
- [ ] バックエンドのエラーメッセージ（バリデーションエラー等）が、フロントエンドの汎用エラーメッセージで上書きされて消えていないか（`TaskApiError` のように、サーバーからの詳細メッセージを優先して表示する仕組みになっているか）
- [ ] API 呼び出し失敗時に画面上で何も起きず、ユーザーがエラーに気づけない箇所がないか（D&D の並び替え失敗、一括削除失敗など）
- [ ] フロントエンドで失敗時にローカルの状態だけ更新し、サーバー側との不整合に気づけない実装になっていないか（楽観的更新後、失敗時に元の状態へロールバックしているか）
- [ ] try-catch で例外の型を判定せず、すべて同じ汎用メッセージにしてしまい、原因切り分けができなくなっていないか

## ステップ5：報告と対応

1. 見つかった問題点を一覧化し、ユーザーに報告する
2. 対応方針（修正 or ドキュメント更新）について、判断が必要なものはユーザーに確認する
3. 修正後、ステップ1の静的解析・ビルドチェックを再実行して確認する
4. ブラウザで動作確認する（`http://localhost:5173`）
5. `create-pr` スキルを呼び出してチェックリストを実行し、PRを作成する
